# Optional external-agent benchmark protocol

Status: not run. The eight-tool desk review in [research](24_RESEARCH_AND_POSITIONING.md) contains no performance ranking. This protocol makes a future named comparison fair and reviewable; it is P2 and must not delay the working entry.

## Questions to separate

1. Do fixed candidate patches from an agent meet the declared engineering contracts?
2. Does the same agent, given BenchProof's sanitized constraint/impact feedback, repair more effectively?
3. Does BenchProof's gate reject invalid patches even when visible tests pass?

The third question can be answered on V12/V6 without paid competitor access. The first two require actual configured product runs. A product's performance without feedback is not the same as the value of the assurance layer when attached to it.

## Access and product identity

Select at most three actually accessible tools after P0 and final internal evaluation are stable. Record product/build, plan/entitlement, model selection if exposed, surface, instructions, plugins, approval mode, network access, date and available usage. Use documented canonical product naming; Windsurf's redirect to Devin Desktop is an overlap to disclose, not proof of two independent systems.

Unavailable tools are NOT_RUN, never assigned zero. Do not buy subscriptions, bypass access controls or invent a mock competitor. Existing authorization and rights must cover any live runs and public result artifacts.

## Matched task contract

Use the same source commit, synthetic task intent, accepted constraints, visible tests and patch restrictions. Keep hidden expected values/truth/check implementations outside every agent. Remove answer-revealing filenames. Freeze prompts/tasks before the first run.

Match elapsed time, number of patch attempts, tool executions and token limits where observable. If a product cannot expose/enforce a token cap, disclose that difference and do not claim an exactly matched cost comparison. Include setup, approval interruptions and automatic retries in records. Latency may differ by surface/network/hardware; show those conditions.

Same model across tools is often impossible. Such a comparison evaluates configured products, not isolated orchestration quality. Do not attribute a difference solely to the product architecture or to its underlying model.

## Minimal run design

Choose a named four-case subset before measurement: one AC, one MC, one CI/ID only if supported, and one clean control. Use three predetermined trials per case per tool (twelve trials per configured product). Independent fresh sessions avoid carryover; record any product persistence that cannot be reset. Keep this subset separate from the held-out internal R12 claims if outcomes guide tuning.

For each trial save task/prompt, approved source, patch, tool/action summary, timing, visible results and limitations. Score the final candidate with the same trusted evaluator. A timeout, failed task or absent patch remains in the assigned trial denominator. Release only artifacts whose terms/rights allow it; sanitize transcripts.

For an assurance-assisted experiment, pair original and feedback-assisted sessions under the predeclared design. Provide identical public task intent; only the runtime's sanitized impact/failure feedback is added in the treatment. Keep budgets matched or disclose additional cost. Randomize/counterbalance order where possible. Do not reuse a remembered correct patch in a “fresh” assisted trial.

## Outputs and metrics

| Output | Definition |
| --- | --- |
| Independent repair outcome | Intended defect resolved and all required contracts pass / all assigned faulty trials |
| Clean behavior | Unjustified/harmful patch and false confirmed issue counts / clean trials |
| Gate effect | Same fixed patch smoke result versus protected result; invalid accepted and valid rejected/unknown counts |
| Assistance effect | Paired outcomes, added time/usage and any unmatched limits |
| Operational experience | Observable errors/approvals/availability, not subjective personality ratings |

Separate code success from the product's own “done” message. Report unique tasks, repeated trials and actual sample sizes. A small synthetic subset cannot establish that a tool is generally best or worst. Include failures, null findings, versions and configuration differences.
